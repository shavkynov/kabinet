  - добавлены отрицательные проверки, в частности буквальное «в роли Гамлета» не должно считаться канцеляризмом.

Эти изменения внесены в GitHub, но **не исполнены локально**. Не считать тесты пройденными.

## Обязательная последовательность завершения

### 1. Получить актуальный код и проверить изменения

1. Переключиться на `fix/style-analysis-coverage`.
2. Проверить `git status`, `git log` и diff относительно `main`.
3. Убедиться, что в diff только ожидаемые изменения и этот handoff-файл.
4. Проверить регулярные выражения в `src/style.js` на корректность Unicode-режима, границ слов и склоняемых форм.
5. Проверить, что каждый новый шаблон возвращает точный диапазон подсветки, а не только часть выражения.

### 2. Запустить автоматические проверки

Требуется Node.js версии, совместимой с проектом, и зависимости из lock-файла.

Выполнить:

```bash
npm ci
node --test test/style.test.js
node --test test/analysis-ui.test.js
npm test
npm run check
npm run build
```

Если полный набор тестов занимает слишком много времени, сначала запустить два профильных теста, затем полный набор. Не заменять полный набор только профильными.

При любой ошибке:
- сохранить полный вывод;
- определить, новая ли это ошибка или существующая;
- исправить регрессию;
- повторить профильные тесты и полный набор.

### 3. Проверить все восемь категорий на русской прозе

Категории объявлены в `renderer/analysis.js` и реализованы в `src/style.js`:

- `chancery` — канцелярит и штампы;
- `weak` — слабые/фазовые глаголы;
- `tell` — называние эмоций и посреднические конструкции;
- `chain` — цепочки отглагольных существительных;
- `remark` — перегруженные авторские ремарки;
- `redund` — плеоназмы и тавтология;
- `which` — скопление придаточных с «который»/«что»;
- `own` — избыточные притяжательные местоимения.

Для каждой категории:
1. Добавить положительные тесты на несколько грамматических форм и падежей.
2. Добавить отрицательные тесты на омонимы, прямое значение выражения и нормальные литературные конструкции.
3. Проверить диапазоны `start/end`: они должны выделять ровно нужный фрагмент, не захватывая соседние слова и знаки препинания без необходимости.
4. Проверить подсказку `tip`: она должна объяснять наблюдение, а не объявлять конструкцию ошибкой.
5. Проверить, что прямая речь исключается там, где это предусмотрено правилами, но авторский текст после слов автора анализируется.

Не расширять словари и регулярные выражения только ради увеличения числа срабатываний. Цель — полезные и объяснимые замечания, а не максимальная плотность подсветки.

### 4. Обязательная проверка пользовательского контрольного фрагмента

В предыдущем обсуждении пользователь предоставил большой литературный фрагмент о Драко и Теодоре Нотте, Нарциссе Малфой и послевоенном восстановлении.

Использовать именно исходный текст без редактирования и нормализации. Если он недоступен в истории другому агенту, запросить его у пользователя. Не восстанавливать текст по пересказу и не сочинять его заново.

Важно: не добавлять неопубликованный текст пользователя в публичный репозиторий. Для проверки:
- хранить корпус локально вне репозитория или во временном тестовом файле, который не коммитится;
- прогнать `scanStyle` с каждой категорией отдельно и со всеми восемью категориями вместе;
- сохранить отчёт: категория, точный фрагмент, подсказка, позиция;
- вручную классифицировать каждое срабатывание как полезное, ложное или спорное;
- отдельно выписать ожидаемые замечания, которые анализатор пропустил;
- после настройки повторить прогон и сравнить результаты.

Известные кандидаты, которые обсуждались, но не являются автоматически доказанными ошибками:
- «прикладывает значительные усилия» — `chancery`;
- «выступая в роли посредника» — `chancery`;
- «смотрит на неё с настоящим удивлением» — `tell`;
- «происходят значительные перемены» — возможно слишком общая формулировка, но это не следует ловить без контекстного правила;
- «голос дрожит от избытка эмоций» — возможно называние/обобщение эмоции;
- повтор «вздыхает» в близких предложениях — это лексический повтор, а не обязательно текущая категория `redund`.

Не превращать эти примеры в обязательные срабатывания без проверки контекста.

### 5. Проверить интеграцию редактора и интерфейс — критическая часть

Статический анализ выявил, что `renderer/analysis.js` вызывает `scanStyle` только когда:
- язык интерфейса `LANG === 'ru'`;
- хотя бы одна категория из `STYLE_CATS` включена в `cfg.cats`.

Если ни одна категория не включена, анализатор возвращает пустой набор Decorations. В `renderer/app/21-look.js` начальное значение `settings.an` — пустой объект, а загрузчик восстанавливает только категории, явно включённые в сохранённых настройках. Само по себе это не доказывает ошибку: пользователь может включить категории в панели настроек. Но это необходимо проверить на реальном UI.

Найти точную реализацию `applyAnalysisSettings` и весь путь данных:
1. Где пользователь включает/выключает восемь стилевых категорий.
2. Где значение записывается в `settings.an`.
3. Где настройки сохраняются в `localStorage`.
4. Как `applyAnalysisSettings` формирует `cats` для `TextAnalysis.getConfig`.
5. Вызывается ли `refreshAnalysis(editor)` после каждого изменения категорий.
6. Не перезаписывает ли загрузка проекта/документа настройки глобальные настройки анализа.
7. Сохраняются ли включённые категории после перезапуска приложения.

Проверить вручную в приложении:
- новый профиль/чистые настройки;
- включить только `chancery`, затем только `tell`, затем все восемь категорий;
- вставить текст с заведомо каноническими примерами;
- убедиться, что подсветка появляется без перезагрузки документа;
- выключить категорию — её метки и счётчик должны исчезнуть;
- снова включить — метки должны вернуться;
- перезапустить приложение и проверить сохранение;
- проверить русский и английский интерфейсы: стилевые правила должны применяться только к русскому тексту, как задумано;
- проверить короткий документ и большую главу, включая отложенный пересчёт через `lazyView`.

Отдельно проверить, не путается ли симптом `no_marks` с функцией отображения скрытых символов (¶, пробелы, табуляции). Это другая подсистема, управляемая `settings.marks` и `settings.marksSpaces`, и она не должна влиять на стилевые Decorations.

### 6. Проверить кэширование и пересчёт

В `renderer/analysis.js` есть кэш результатов по ProseMirror node. Убедиться, что:
- при изменении текста меняется узел и анализ пересчитывается;
- при изменении только настроек категорий меняется сигнатура категорий и анализатор вызывается заново;
- при изменении исключений «Не отмечать здесь» метки и счётчики обновляются;
- при больших документах отложенный пересчёт действительно завершается и снимает stale-состояние;
- кэш не сохраняет результат со старой конфигурацией.

Если обнаружится дефект, добавить регрессионный тест в `test/analysis-ui.test.js` или отдельный тест с harness, а не ограничиваться ручной проверкой.

### 7. Критерии готовности

Работа готова к Pull Request, только если:
- профильные и полные тесты проходят;
- `npm run check` и `npm run build` проходят;
- добавлены тесты на положительные и отрицательные случаи каждой изменённой категории;
- контрольный литературный фрагмент проверен вручную, ложные срабатывания классифицированы;
- подтверждено, что настройки включения категорий реально доходят до редактора и запускают пересчёт;
- подтверждено, что метки появляются после включения категорий и сохраняются после перезапуска;
- в PR перечислены изменения, результаты команд и известные ограничения.

Не сливать ветку в `main` автоматически. Сначала показать пользователю результаты и PR для проверки.
