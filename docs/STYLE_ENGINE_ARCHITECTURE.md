# Архитектура локального лингвистического анализатора стиля

Статус: **исследовательский аудит завершён частично; выбор исполняемого NLP-движка заблокирован проверкой лицензий и контрольным прогоном на художественном корпусе**.

Дата аудита: 2026-11-19. Базовая ветка: `fix/style-analysis-coverage`, исходный коммит: `a619e087e72391a2ddea3888fbe69a1a05cf95c9`.

## 1. Цели и ограничения

Анализатор должен работать полностью локально, без LLM, облачных API, сетевых запросов и передачи пользовательского текста за пределы устройства. Восемь категорий сохраняются:

| ID | Категория | Основной языковой сигнал |
|---|---|---|
| `chancery` | Канцеляриты | Номинализации, отвлечённые существительные, пассивные/безличные конструкции, семантически пустые глаголы и их сочетания |
| `weak` | Слабые глаголы | Фазовые/связочные/общезначимые глаголы, низкая событийная нагрузка в контексте |
| `tell` | «Назвал, а не показал» | Предикаты эмоций/состояний и ментального восприятия; только эвристический модуль |
| `chain` | Цепочки существительных | Вложенные именные группы, зависимые генитивы, глубина и длина NP |
| `remark` | Ремарки при репликах | Границы прямой речи, синтаксическая структура авторской ремарки, повтор и избыточность |
| `redund` | Лишние слова и тавтология | Повтор лемм, семантическая близость/включение, дублирование смысловых ролей |
| `which` | Лавина «который» и «что» | Относительные/изъяснительные придаточные, глубина вложенности, длина цепочки зависимостей |
| `own` | Лишние «свой» и «его» | Посессивная зависимость, субъект/владелец, антецедент и локальная кореференция |

Качество оценивается не числом подсветок. Высокая точность важнее полноты. Все выводы анализатора — редакторские сигналы, не грамматические приговоры.

## 2. Фактическая архитектура приложения на базовом коммите

Приложение — Tauri 2 с Rust-оболочкой и ProseMirror/Tiptap-интерфейсом. В репозитории существуют два слоя:

- основной frontend и существующий анализ текста: `renderer/analysis.js`, `src/style.js`, `src/morph.js`, `src/speech.js`;
- переносимая Tauri-версия: `experiments/tauri-app/src-tauri` и `experiments/tauri-app/core`.

Текущий стилевой анализ вызывается синхронно из `renderer/analysis.js`: `styleOf()` → `scanStyle(text, words, cats, sentences)` из `src/style.js`. Результат переводится в ProseMirror inline Decorations. Для абзацев уже есть WeakMap-кэш, ключом служит узел редактора; сигнатура кэша стиля учитывает включённые категории. Настройки восьми категорий хранятся в `settings.an`, список категорий — `AN_CATS`, стилевые категории — `STYLE_CATS`. Счётчики, диапазоны для навигации и исключения формируются в плагине анализа.

`src/morph.js` прямо описывает себя как приблизительный разбор по окончаниям и частотным спискам, без полноценного словаря. `src/style.js` использует фиксированные регулярные конструкции и эвристики. `src/speech.js` определяет диапазоны реплик регулярной обработкой кавычек и тире. Эти модули не являются пригодным базовым синтаксическим анализатором для новой архитектуры.

В `package.json` нет зависимости от Python/NLP-моделей. В Tauri Rust workspace нет готового NLP-парсера. Следовательно, новый движок потребует явного слоя интеграции, поставки моделей и обновления сборок для Windows, macOS и Linux. Ветка не должна считать наличие Rust/Tauri достаточным доказательством переносимости конкретной NLP-библиотеки.

## 3. Исследование кандидатов

### 3.1 Stanza

**Возможности.** Официальные UD-пайплайны дают сегментацию, токенизацию, POS, морфологические признаки, леммы и dependency parsing. Для русского есть модели GSD, SynTagRus и Taiga. Это наиболее полная из рассмотренных готовых систем для получения единого структурированного разбора.

**Качество.** В опубликованной таблице Stanza для UD SynTagRus указаны UPOS 98.06, леммы 97.65, UAS 93.26 и LAS 90.90. Это benchmark на тестовом разбиении конкретного UD treebank, не оценка качества стилистических замечаний и не гарантия на пользовательской прозе. SynTagRus включает современную художественную прозу, научно-популярные, газетные и журнальные тексты.

**Скорость и ресурсы.** В таблице сравнения Slovnet (сопоставление на GramEval2020) для Stanza приведены 591 MB дисковых артефактов, 890 MB RAM и 12 предложений/с для синтаксиса; для морфологии — 591 MB, 393 MB RAM и 92 предложения/с. Это значения среды авторского benchmark, а не измерения на компьютерах пользователей. Отдельный репозиторий Stanza Russian на Hugging Face занимает 3.39 GB целиком; этот размер нельзя считать размером минимального набора файлов для одного русского пайплайна.

**Интеграция.** Stanza — Python/PyTorch; готового Rust API нет. Реалистичная поставка — локальный sidecar с Python runtime и заранее включёнными файлами моделей либо экспорт/порт отдельных моделей. Sidecar должен работать как постоянный процесс с JSONL-протоколом, а не запускаться заново на каждый абзац. Нужны отдельные сборки и проверка бинарных зависимостей для трёх ОС.

**Лицензии.** Код Stanza распространяется под Apache 2.0. Однако документация Stanza прямо предупреждает, что лицензия UD language packs не всегда однозначна. SynTagRus обозначен как CC BY-NC-SA 4.0. До выяснения прав на распространение весов нельзя включать SynTagRus-модель в публичный релиз приложения, особенно если возможна коммерческая эксплуатация. Не считать Apache 2.0 лицензией обучающих данных.

**Вывод.** Лучший контрольный кандидат по структурному качеству для русского художественного текста, но пока не утверждён для поставки: нужно разрешить лицензионный вопрос и измерить реальный размер минимального пакета.

### 3.2 UDPipe 1

**Возможности.** Нативная C++ библиотека и CLI; токенизация, POS, лемматизация и зависимости. Есть готовые модели UD и биндинги для нескольких языков программирования. Поддерживает Windows, macOS и Linux.

**Качество.** В сравнительном benchmark Slovnet для художественного подкорпуса синтаксический LAS UDPipe — 0.876, UAS — 0.910; морфологическая accuracy — 0.957. Эти показатели получены на конкретной версии моделей и разбиении GramEval2020. Они не эквивалентны результатам Stanza на другом treebank/протоколе.

**Скорость и ресурсы.** В том же сравнительном тесте: около 45 MB дисковых артефактов, 242 MB RAM, 56.2 предложений/с для синтаксиса. На странице UDPipe 1 указана скорость порядка 1000 слов/с на одном CPU для системы в целом. Это сторонние/проектные benchmark-данные, не измерение в Кабинете.

**Интеграция.** Наиболее естественный кандидат для нативной интеграции в Rust через C ABI/FFI или отдельную библиотеку. Это позволяет избежать Python runtime. Потребуются сборка/линковка C++ для трёх платформ, упаковка модели, контроль ABI и smoke-тесты установщиков. Сам по себе UDPipe не решает архитектуру асинхронного анализа редактора.

**Лицензии.** Исходный код UDPipe — MPL 2.0. Официальная документация указывает, что готовые модели UDPipe 1 распространяются для некоммерческого использования под CC BY-NC-SA; нужно отдельно проверять конкретную модель и источник данных. Это блокер для распространения без подтверждённых прав.

**Вывод.** Хороший технический кандидат для лёгкой нативной интеграции, но готовая модель не проходит лицензионный gate без дополнительного разрешения.

### 3.3 UDPipe 2

**Возможности.** Более сильная нейросетевая морфология и синтаксис; доступны UD модели, включая русский SynTagRus. Однако UDPipe 2 — Python-прототип, не выполняет токенизацию и требует больше вычислений. Для локального приложения понадобится отдельная сегментация/токенизация и Python runtime.

**Качество.** Для Russian SynTagRus в таблице UDPipe 2 (UD 2.17) опубликованы на raw text: UPOS 98.74, леммы 98.53, UAS 94.18, LAS 92.73; при gold tokenization: UPOS 99.05, леммы 98.81, UAS 94.91, LAS 93.43. Это тестовое разбиение UD 2.17, а не художественная независимая выборка Кабинета. Сопоставлять эти цифры с другими таблицами без оговорок нельзя.

**Скорость/память.** В таблице моделей UDPipe 2 не приведены сопоставимые показатели скорости и памяти. В статье о прототипе UDPipe 2 (CoNLL 2018) приведены 111 слов/с на одном CPU-потоке, 517 слов/с на восьми потоках и 2320 слов/с на одном GPU-потоке (TensorFlow 1.5.1); это старый исследовательский benchmark, не измерение актуальной модели SynTagRus и не прогноз производительности в Кабинете. Потребление памяти и размер русского набора файлов для целевой конфигурации отдельно не опубликованы в изученных источниках — измерить локально.

**Интеграция и лицензии.** Python-only prototype усложняет упаковку в Tauri. Страница прототипа UDPipe 2 говорит об отсутствии токенизации, тогда как описание пакета моделей UD 2.17 включает tokenizer; способ использования токенизатора в текущей версии runtime нужно проверить отдельно. UD 2.17 models распространяются под CC BY-NC-SA. Не утверждать автономность поставки до получения и включения конкретных файлов; не использовать REST-сервис LINDAT — это нарушило бы требование полностью локальной обработки.

**Вывод.** Качественный benchmark-кандидат, но хуже подходит как встроенный runtime; лицензия модели также требует разрешения.

### 3.4 Natasha / Slovnet / Razdel / Navec

**Возможности.** Natasha предоставляет русскую сегментацию (Razdel), морфологию и синтаксис (Slovnet), лемматизацию через MorphVocab/Pymorphy и компактные эмбеддинги Navec. Slovnet возвращает зависимости в формате head/relation и может обрабатывать предложения пакетами.

**Качество.** В опубликованной таблице GramEval2020 Slovnet обучен на новостном наборе; на fiction его морфологическая accuracy — 0.905. Для синтаксиса на fiction: UAS 0.806, LAS 0.776. Для сравнения в той же таблице: Stanza LAS 0.895, UDPipe LAS 0.876, spaCy LAS 0.874. На poetry Slovnet LAS 0.469, что подчёркивает доменную чувствительность. Эти значения не позволяют без проверки переносить выводы на современную авторскую прозу, но указывают на риск для литературного текста.

**Скорость и размер.** Авторы Slovnet сообщают для базовых моделей morphology+syntax около 27 MB дисковых артефактов, 125 MB RAM и 450 предложений/с для синтаксиса; morphology отдельно — 27 MB, 115 MB RAM, 532 предложения/с. Модельные архивы: morphology 2 MB, syntax 3 MB; для полной системы нужен также Navec embedding archive и словари. Значения скорости/памяти — upstream benchmark, а не тест на целевом устройстве.

**Интеграция.** CPU-only inference через NumPy, малый размер моделей. Самая компактная готовая связка. Но официальная Natasha API и Slovnet — Python. Sidecar-подход возможен; нативный Rust-порт потребует отдельной реализации вычислительного графа/экспорта и не должен предполагаться готовым. Указанная upstream API оптимизирована для новостей, авторы прямо предупреждают о возможном падении качества на других доменах.

**Лицензии.** Репозитории Natasha и Slovnet имеют MIT-лицензию. Но лицензии весов, Navec embeddings и исходных корпусов следует фиксировать по каждому конкретному архиву до поставки. Наличие MIT у кода не автоматически лицензирует все веса/данные.

**Вывод.** Самый привлекательный вариант по скорости, размеру и RAM; не подходит как единственный парсер без оценки на художественном корпусе. Рассматривать как быстрый baseline/возможный дополнительный parser после лицензирования и измерения качества.

### 3.5 OpenCorpora

**Назначение.** Морфологический словарь и размеченный корпус, не синтаксический парсер. Может служить лексическим источником, проверочным ресурсом и основой для словарных признаков; не даёт dependency tree и не снимает всю омонимию автоматически.

**Ресурсы.** Страница загрузок сообщает о XML-корпусе примерно 1.1 млн слов и морфологическом словаре; указана CC BY-SA 3.0. В момент открытия страницы сайт отдавал nginx placeholder, поэтому текущую доступность файлов нужно перепроверить при практической загрузке.

**Интеграция.** Данные можно конвертировать в компактный локальный словарь/SQLite или встроенный индекс. Важно соблюдать атрибуцию и share-alike требования для производных данных. Для морфологического runtime проще использовать pymorphy3 с локальным словарным пакетом, чем самостоятельно реализовывать OpenCorpora XML.

**Вывод.** Полезный лексический ресурс, не альтернатива синтаксическому анализатору.

### 3.6 pymorphy3

**Назначение.** Морфологический анализатор/генератор форм для русского и украинского языков. Использует словари, собранные из OpenCorpora XML, возвращает набор возможных разборов и нормальную форму; неизвестные слова обрабатывает эвристически.

**Качество/ограничения.** Подходит для морфологической проверки и fallback, но без контекстного синтаксического парсера сохраняет омонимию. Не выдаёт dependency tree.

**Интеграция.** Python package; локальные словари доступны отдельными пакетами. Официально поддерживает Python 3.9–3.14. В Tauri потребуется sidecar или отдельный порт. MIT-лицензия пакета не отменяет требований лицензии словарных данных.

**Вывод.** Сильный кандидат на роль вспомогательного морфологического словаря, но не базового движка.

### 3.7 RuWordNet

**Назначение.** Семантический тезаурус: синсеты существительных, глаголов и прилагательных, гиперонимия/гипонимия, часть-целое, антонимия, доменные связи, причинность и следование для глаголов. Это полезно для семантических классов глаголов, синонимии и повторов, но не для морфологии или синтаксиса.

**Ресурсы и лицензия.** Сайт указывает 111.5 тыс. слов/выражений и 49.8 тыс. синсетов (29,297 noun, 12,865 adjective, 7,636 verb). На странице одновременно сказано, что тезаурус распространяется для некоммерческого использования и что он доступен по CC BY-SA 4.0; XML-файлы предлагается запрашивать у автора. Это противоречие должно быть разрешено письменно до включения ресурса в дистрибутив.

**Вывод.** Не включать в приложение до получения XML и юридически ясных условий распространения. До этого можно проектировать абстракцию семантического словаря и использовать собственные permissive-ресурсы.

### 3.8 spaCy Russian и DeepPavlov

**spaCy.** В сравнительной оценке Slovnet для fiction морфологическая accuracy — 0.942, синтаксический LAS — 0.874; в той же оценке приведены 140 MB артефактов, 579 MB RAM и 41 предложение/с. Это достойный контрольный кандидат, но Russian pipeline также нужно проверить по актуальности, домену и лицензии модели; Python runtime остаётся.

**DeepPavlov.** В сравнительной оценке BERT-вариант показывает fiction LAS 0.929, но авторская таблица указывает 1,427 MB артефактов и 8,704 MB RAM, скорость 75 предложений/с на GPU. Это тяжёлый кандидат для минимальной desktop-поставки и не гарантирует приемлемую скорость на CPU. Требуется отдельная проверка лицензии конкретной модели и её весов.

## 4. Предварительное решение по движку

**Ни одна готовая модель не утверждена для production на этом этапе.** Выбирать библиотеку только по benchmark на чужом корпусе нельзя.

Предлагаемый порядок контрольного сравнения:

1. Stanza Russian SynTagRus — эталон качества и основной кандидат, если разрешена лицензия на модель/данные и размер приемлем.
2. UDPipe 1/2 — контрольная линия, особенно если удастся получить permissive модель или отдельное разрешение на распространение.
3. Natasha/Slovnet — быстрый компактный baseline, но с известным снижением качества на fiction/poetry.
4. spaCy Russian и DeepPavlov — дополнительные сравнительные кандидаты, если совместимы лицензии и упаковка.

Перед окончательным выбором необходимо получить для каждого конкретного набора весов: URL/версию, SHA-256, лицензию кода, лицензию весов, лицензию train/dev/test корпуса, размер после распаковки, пиковую RAM, cold-start и throughput на одном и том же оборудовании. Если лицензия не позволяет включить модель в приложение, исключить её независимо от качества.

## 5. Предлагаемая архитектура приложения

### 5.1 Разделение слоёв

1. **Text adapter** — сохраняет точные UTF-16 offsets исходного текста для ProseMirror; нормализация не должна менять координаты.
2. **Sentence/token layer** — границы предложений и токенов; отдельно обрабатывает кавычки, тире, сокращения, инициалы, числа и многоточия.
3. **Morphology layer** — UPOS, XPOS (если есть), lemma, Case, Number, Gender, Animacy, Aspect, VerbForm, Voice, Mood, Tense, Person и confidence/ambiguity.
4. **Dependency layer** — head index, relation, sentence ID, offsets; внутреннее представление нейтрально к конкретному parser.
5. **Context layer** — прямая речь, абзацы, границы предложений, субъект/объект, кандидаты-антецеденты, локальные цепочки.
6. **Style rules** — восемь независимых модулей; ни один модуль не должен иметь собственный второй парсер.
7. **Scoring/explanations** — confidence, причины и ограничения; калибровка только на размеченном корпусе.
8. **ProseMirror adapter** — преобразование результата в Decorations, counters и navigation ranges.

### 5.2 Унифицированная структура разбора

Для каждого предложения движок должен возвращать структуру вида:

```json
{
  "sentence": { "start": 0, "end": 42 },
  "tokens": [
    {
      "text": "решение",
      "lemma": "решение",
      "upos": "NOUN",
      "feats": { "Case": "Acc", "Number": "Sing", "Gender": "Neut" },
      "head": 3,
      "deprel": "obj",
      "start": 12,
      "end": 19,
      "confidence": null
    }
  ],
  "parser": { "name": "adapter-id", "version": "pinned-version" }
}
```

Это контракт, а не утверждение, что выбранный парсер отдаёт probability. Если модель не предоставляет confidence, хранить `null`; не синтезировать вероятность из уверенности автора правила.

Offsets в UI — UTF-16 code units. Adapter обязан переводить offsets модели (часто Python Unicode code points или byte offsets) в UTF-16 без сдвига на кириллице, emoji и комбинируемых символах.

### 5.3 Runtime и асинхронность

Текущий стилевой анализ синхронный. Нейросетевой парсер нельзя запускать синхронно внутри ProseMirror state apply.

Предлагаемый путь:

- Tauri Rust слой управляет одним локальным parser sidecar, если выбран Python-runtime. Sidecar запускается один раз и принимает JSONL-запросы; стандартные потоки не содержат пользовательских текстов в логах.
- Rust IPC принимает batch изменившихся абзацев и возвращает JSON с теми же paragraph IDs и revision hashes.
- JS plugin запускает анализ из view/update, не блокируя ввод; результат применяется транзакцией с meta.
- Ответ отбрасывается, если document revision, paragraph hash или набор категорий уже изменились.
- WeakMap/cache хранит результаты по immutable paragraph node + parser version + normalized text hash. Изменение категории не должно заставлять заново парсить текст — повторно запускается только rule layer.
- Большие главы анализируются пакетами/по изменившимся абзацам; пока ответ не готов, старые Decorations либо помечаются stale, либо убираются по заранее заданной политике, но никогда не отображаются на неверных позициях.
- Для отключённого стилевого анализа sidecar не должен стартовать и не должен потреблять RAM.
- Ошибка parser не превращается в «0 замечаний»: UI показывает недоступность анализа и сохраняет редактор работоспособным.

Если будет выбран нативный C++/Rust runtime, JSONL-контракт и асинхронная модель сохраняются, меняется только transport/adapter.

### 5.4 Политика локальности

- Все модели и словари входят в подписанный дистрибутив или устанавливаются из локального пакета; никаких скачиваний при первом запуске.
- В CSP/permissions не добавлять сетевые endpoint для анализа.
- Parser sidecar не имеет сетевой функциональности; в тесте проверять отсутствие исходящих соединений во время анализа.
- Тексты не включать в логи, crash reports, telemetry или CI artifacts.
- Документировать путь и SHA-256 всех поставляемых ресурсов.
- Лицензионные файлы и notices поставлять рядом с ресурсами.
- Модельная версия закрепляется lock manifest, не обновляется автоматически.

## 6. Алгоритмы восьми категорий

### 6.1 `chain` — цепочки существительных (высокая реализуемость)

- Из dependency tree извлекать именные группы вокруг NOUN/PROPN.
- Учитывать `nmod` в Gen, вложенные `nmod`, `amod`, `compound`, `appos`, зависимые отглагольные существительные.
- Считать глубину генитивной цепочки, число зависимых именных узлов, длину NP и число номинализаций.
- Не считать соседние существительные проблемой сами по себе; исключать имена, термины, устойчивые названия, перечни, приложения и естественные количественные конструкции.
- Высокая уверенность возможна при глубокой вложенной цепочке + нескольких номинализациях; средняя — при длинной NP без номинализаций; низкая — при частичном/ошибочном parse.

### 6.2 `which` — придаточные (высокая реализуемость)

- Использовать `acl:relcl`, `ccomp`, `advcl`, `csubj`, `parataxis`, `mark` и связи с относительными местоимениями.
- Считать не все вхождения «что»/«который», а реальные клаузы, глубину вложенности и число зависимых клауз на предложение.
- Различать вопросительное/указательное «что», частицы и союзное слово.
- Учитывать длинные бессоюзные конструкции и придаточные без явного «который».
- Уверенность зависит от согласованности parse и сегментации.

### 6.3 `chancery` — канцеляриты (средняя реализуемость)

- Выявлять номинализации по суффиксам/словарю и морфологии; связывать их с управляющими глаголами и зависимыми дополнениями.
- Анализировать пассив/безличность, цепочки отвлечённых существительных, глаголы-операторы (осуществлять, производить, проводить, оказывать) и отвлечённые объекты.
- Оценивать совместное присутствие сигналов, а не одно слово.
- Не объявлять всякий пассив или отглагольное существительное канцеляритом: научная, юридическая, административная и историческая речь может требовать их.
- Ошибки вероятны на авторской стилизации, терминологии, архаизмах и неоднозначной словообразовательной морфологии.

### 6.4 `weak` — слабые глаголы (средняя реализуемость)

- Классифицировать глаголы по семантическим классам: фазовые, связочные, общезначимые, локативные/состояния, речевые/перцептивные.
- Использовать dependency: связь фазового глагола с xcomp/infinitive; глагол-связка + именная/прилагательная часть; конструкция «находиться + локатив».
- Оценивать наличие смыслового предиката в зависимой части и информационную нагрузку глагола в контексте.
- Не отмечать «быть», «стать», «начать», «находиться» автоматически: они могут выражать время, состояние, фазу или изменение смысла.
- Лексические классы требуют словаря и ручной ревизии; контекстная оценка ограничена.

### 6.5 `remark` — ремарки при репликах (средняя реализуемость)

- Сначала извлечь speech spans и attribution clauses из структуры кавычек/тире и синтаксических связей.
- Разделять слова автора и текст реплики; существующий `speechRanges` оставить временным fallback, но не считать достаточным.
- Анализировать длину ремарки, число зависимых обстоятельств/деепричастных оборотов, цепочки определений, повтор глагола речи в соседних репликах, избыточные наречия/эмоциональные пояснения.
- Учитывать инверсию «— …, — сказал он» и разорванные реплики; вложенные кавычки и несколько тире требуют тестов.
- Ложные срабатывания возможны на авторски значимых жестах и намеренно подробных ремарках.

### 6.6 `redund` — лишние слова и тавтология (средняя реализуемость)

- Лемматизировать и искать близкие повторения в ограниченном окне; использовать синтаксические роли и семантические классы.
- Для плеоназма нужна связь смыслового включения (например, родовой/видовой компонент) или известная пара; простая синонимия не является доказательством избыточности.
- Считать повтор леммы, перефразирование и повтор события отдельно; учитывать дистанцию, фокус и намеренное повторение.
- RuWordNet может быть дополнительным ресурсом только после юридической проверки; не использовать как обязательную зависимость.
- Семантическая избыточность без дискурсивной модели имеет высокий риск ложных выводов.

### 6.7 `own` — «свой» и «его» (средняя реализуемость)

- Находить Poss=Yes/PRON и possessor/детерминативные зависимости.
- Определять субъект/владельца через `nsubj`, `obj`, `iobj`, локальные клаузы и возвратность.
- Строить ограниченный candidate antecedent set по предложению/соседним предложениям; разрешать только однозначные случаи.
- Снимать подсветку, если местоимение нужно для контраста, смены владельца, снятия неоднозначности или дискурсивного акцента.
- Без полноценной coreference-модели не делать утверждений о дальней кореференции; неуверенные случаи пропускать.

### 6.8 `tell` — «назвал, а не показал» (низкая реализуемость)

Это единственная категория, где допустим шаблонный подход. Использовать локальные шаблоны, словари эмоций/состояний и морфологические признаки. Не заявлять о полном понимании художественного контекста.

Обязательное предупреждение в UI:

> Категория использует шаблоны, словари и эвристики. Она не понимает художественный контекст в полной мере. Возможны пропуски и ложные срабатывания. Обнаруженные фрагменты требуют проверки автором.

### 6.9 Уровни уверенности

Уровни — качественные классы, пока нет размеченной выборки для калибровки:

- **Высокая:** несколько независимых языковых сигналов согласуются; parser не помечен как ошибочный; конструкция подтверждается структурой зависимостей.
- **Средняя:** один сильный структурный сигнал либо несколько слабых; возможна художественная функция.
- **Низкая:** эвристический сигнал, неоднозначный антецедент, неполный parse или слабая семантическая близость.

До калибровки не показывать численные проценты вероятности. Confidence не должен быть просто константой для всей категории.

## 7. Формат результата категории

Каждый результат должен содержать:

```json
{
  "category": "chain",
  "start": 18,
  "end": 57,
  "fragment": "точный фрагмент",
  "explanation": "обнаружена вложенная генитивная цепочка ...",
  "method": ["dependency:nmod", "morphology:Case=Gen", "nominalization"],
  "confidence": "medium",
  "limitations": ["именная группа может быть термином или намеренной стилизацией"]
}
```

`fragment` проверяется по исходным offsets, а не собирается из нормализованных лемм. `method` должен описывать реально использованные сигналы. Ошибки parser и fallback фиксируются отдельно.

## 8. Корпус и метрики

Нужен независимый корпус именно художественной прозы, не только UD SynTagRus и не пользовательский текст из закрытых рукописей.

Предлагаемый корпус:

- 300–500 фрагментов из произведений с разрешённой лицензией или общественного достояния; разнородные жанры, эпохи, авторы и стили.
- Не менее двух разметчиков для style labels; adjudication разногласий третьим проходом.
- Для базового parser отдельно gold CoNLL-U или эквивалентные разметки sentence/token/POS/lemma/dependency на репрезентативном подмножестве.
- Разметка категорий по точным span offsets; несколько допустимых spans и «спорно/не отмечать» разрешены.
- Разделение train/dev/test по авторам и произведениям, не по случайным предложениям, чтобы исключить утечку авторского стиля.
- Контрольные срезы: диалог, авторская речь, архаизация, прямая речь с разорванными ремарками, сложный синтаксис, длинные NP, поэзия/ритмизованная проза, имена и термины.

Метрики для каждой категории отдельно: Precision, Recall, F1, exact-span F1 и relaxed-span F1. Для parser отдельно: sentence segmentation F1/exact sentence, token F1, UPOS accuracy, feature micro-F1, lemma accuracy, UAS/LAS. Отдельно показывать показатели по поддоменам и размер выборки. Не переносить parser LAS в «точность стилевого анализа».

Текущий набор позитивных/негативных unit-тестов в `test/style.test.js` — regression suite существующего regex-механизма, не независимый размеченный корпус. Его нельзя использовать как оценку качества новой архитектуры. Контрольный пользовательский фрагмент из прошлых обсуждений не доступен в этом чате и не должен реконструироваться или попадать в репозиторий.

## 9. План миграции

1. Зафиксировать parser-neutral JSON schema и корпусные fixtures.
2. Собрать одинаковый parser challenge set: segmentation, POS, lemma, features, dependencies, clause nesting, quotes/dialogue, hyphen/dash punctuation.
3. Запустить Stanza, UDPipe и Natasha/Slovnet на одном корпусе и оборудовании; сравнить отдельно художественную прозу и диалоги.
4. Пройти license gate для каждой версии кода, модели, словаря и корпуса.
5. Утвердить parser/runtime только после качества, лицензии, offline packaging и измерений на Windows/macOS/Linux.
6. Реализовать локальный runtime adapter и Rust/Tauri IPC.
7. Перенести `chain` и `which` первыми; только затем строить категории средней реализуемости.
8. Реализовать `tell` отдельно с обязательным предупреждением.
9. Интегрировать async Decorations, cache invalidation, counters, exclusions, navigation и live re-analysis.
10. Удалять старый механизм только после parity checks и прохождения регрессионных тестов.
11. Проверить полный npm/Rust/UI/platform CI на новом HEAD.

## 11. Открытые технические риски

- Лицензии готовых русских моделей и корпусов могут запрещать коммерческое распространение; это блокирует bundle даже при технически успешной интеграции.
- Модели, обученные на новостях, хуже переносятся на художественную прозу и особенно поэзию.
- Dependency parser не даёт coreference и дискурсивное понимание; `own` остаётся ограниченным.
- «Слабость» глагола и канцелярит — стилистические, а не чисто грамматические свойства.
- «Лишнее» слово зависит от смысла, жанра и авторского намерения; тезаурус не решает задачу полностью.
- Прямая речь в русской художественной прозе имеет сложные варианты тире/кавычек и вложенных ремарок.
- UTF-16 offsets, Unicode normalization и редактирование текста должны быть проверены отдельно.
- Sidecar/Python-поставка может значительно увеличить installer size, cold-start и RAM.
- Benchmark-данные upstream нельзя считать измерениями приложения; нужны повторные замеры на одинаковом железе.
