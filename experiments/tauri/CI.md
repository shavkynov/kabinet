# Проверка компиляции экспериментальной версии

Статус: конфигурация CI; успешное выполнение не подтверждено до проверки фактических логов GitHub Actions.

Workflow .github/workflows/tauri-experiment.yml запускается только при push затронутых файлов в experiment/tauri-rust. В main он не добавляется. Actions должны быть включены, а политика репозитория должна разрешать используемые actions. Запуск расходует доступные ресурсы GitHub Actions; лимит задания — 45 минут, устаревшие прогоны отменяются.

## Что проверяется

- Установка frontend-зависимостей по существующему package-lock.json. Загрузка Electron пропускается.
- Существующие тесты test/paste.test.js; это не тест вставки из настоящего Word в WebView.
- Сборка изолированного frontend.
- Release-компиляция Rust с встраиванием frontend через feature tauri/custom-protocol.
- Два окружения: macos-latest и windows-latest. Это не полная матрица ОС и не доказательство поддержки обеих архитектур Mac. Архитектура и toolchain выводятся в лог.

## Артефакты и ограничения

Бинарный файл и сгенерированный Cargo.lock сохраняются на 7 дней. Бинарный файл — не установщик и не подписанный выпуск; на macOS это не пакет .app. Артефакты GitHub могут не сохранять Unix executable bit. Не распространять их как готовую версию для пользователей.

Cargo.lock пока не закоммичен, Rust stable и образы latest обновляются. Первые прогоны служат проверкой совместимости; воспроизводимость не заявляется. После успешного прогона сравнить lockfiles, зафиксировать один совместимый Cargo.lock, версии инструментов и при необходимости SHA используемых actions отдельным изменением. Не генерировать lockfile вручную.

Нет публикации Releases, обновлений, подписи, автоматических коммитов, write-разрешений токена или обращения к облачным секретам. Workflow не запускает интерфейс и не проверяет ввод, PDF, сохранение проектов, синхронизацию либо установку на компьютер пользователя.

## Как оценивать результат

1. Открыть GitHub Actions → Tauri experiment compilation и выбрать прогон нужного коммита.
2. Проверить оба задания, а не только общий факт запуска.
3. При ошибке сохранить имя шага и сообщение из лога; исправлять причину, не обходить её continue-on-error.
4. После зелёной компиляции перейти к запуску тестового окна и ручной матрице из README.md. До этого статус — только «компилируется», не «работает».
