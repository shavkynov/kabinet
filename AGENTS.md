# Инструкции по работе над Кабинетом

## Обязательное начало работы с веткой Tauri

Для ветки `experiment/tauri-rust-finish` каноническое живое ТЗ — `docs/tauri-release-tasks.md`. Каждый агент до начала работы обязан прочитать этот файл целиком вместе с настоящими инструкциями, проверить текущий HEAD и рабочее дерево, выбрать задачи и перепроверить их актуальность в коде. Не использовать старый аудит или PORT-REPORT.md как доказательство состояния текущего HEAD.

При изменении кода обновлять соответствующие задачи ТЗ в том же логическом коммите: статус, SHA проверенного кода, изменённые функции, регрессионные тесты, фактически выполненные команды и результаты, ограничения и остаточные риски. Не удалять незакрытые задачи и историю доказательств. Перед передачей работы оставить следующий шаг. Документационный коммит не считать исправлением дефектов. Новые проблемы добавлять в этот файл, не создавать конкурирующие списки. При одновременной работе агентов перечитывать актуальный файл перед записью, не затирать чужие обновления.

## Главный принцип

Автор устанавливает обновление и продолжает писать. Исправления по возможности незаметны: без новой настройки, повторного входа, обучения, миграционных мастеров и дополнительных подтверждений в штатной работе. Сохранность текста важнее внешней незаметности ошибки.

## Обязательные ограничения

- Не менять привычные действия, сочетания клавиш, формат рукописи и расположение проектов без доказанной необходимости.
- Не добавлять настройки там, где достаточно безопасного автоматического поведения. Не перекладывать технические решения на автора.
- Сохранять существующие настройки, подключения и локальные проекты. Миграции выполнять автоматически, повторяемо и с возможностью восстановления; не удалять исходные данные до проверки результата.
- Не объявлять текст сохранённым, пока запись не подтверждена. При сбое удерживать несохранённый снимок; не сбрасывать его при переходах.
- Сетевые ошибки не должны мешать локальному письму. Повторы выполнять в фоне с ограниченной частотой, без бесконечных уведомлений.
- Не скрывать необратимую потерю данных, небезопасное соединение или невозможность безопасного хранения секрета ради удобства. При отсутствии безопасного автоматического решения требуется редкое, понятное сообщение с конкретным действием.
- Не отключать TLS-проверки, не сохранять секреты открытым текстом и не добавлять телеметрию ради незаметности исправления. Не менять адрес сервера и не отправлять пароль на другой адрес автоматически.
- Не переписывать пользовательские Markdown-файлы ради форматирования или оптимизации.

## Порядок изменения кода

1. Воспроизвести проблему и проверить её актуальность в текущем коде. Предварительный статический аудит не является доказательством воспроизведения.
2. Добавить регрессионный тест, включая сбои диска, сети и закрытие окна, если они относятся к изменению.
3. Выбрать минимальное совместимое исправление. Не совмещать его с несвязанным рефакторингом.
4. Проверить штатный сценарий: после обновления автор открывает прежний проект и продолжает работу без новых действий.
5. Выполнить npm ci, npm test и npm run check в подходящей среде. Проверить затронутые платформы и сборку; не заявлять о выполнении команд, если они не запускались.
6. Отдельно указать ограничения, невыполненные проверки и необходимость ручной проверки интерфейса.

## Документация

- План предложений: docs/improvement-plan.md. Он не является списком уже выпущенных исправлений.
- README.txt — пользовательская инструкция; CHANGELOG.txt — фактически выпущенные изменения. Не смешивать их с внутренним аудитом.
- Не создавать дублирующий README.md без отдельного решения о единственном источнике пользовательской документации и совместимости сборочных скриптов.
- Описывать реализованное отдельно от запланированного. Не обещать абсолютную сохранность или отсутствие уязвимостей.
