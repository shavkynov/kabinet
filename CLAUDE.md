# Кабинет — инструкции для Claude

Редактор для писателя на Electron. Основная платформа — macOS; автор общается по-русски и не является программистом. Интерфейс также поддерживает английский. Приоритет — сохранность пользовательских данных и небольшие, проверяемые изменения.

## Рабочий порядок

1. **Сначала локализуй задачу.** Используй `npm run map -- app` для карты функций; ищи определения и вызовы через `grep`. Читай только целевые файлы, их непосредственные зависимости и относящиеся к задаче тесты. Не перечитывай весь проект без конкретной причины.
2. **Проверь актуальное состояние перед изменением.** Проект может меняться параллельно. Не затирай уже сделанную работу и не предполагай, что ранее увиденный код всё ещё актуален.
3. **Делай минимальную правку.** Не рефактори соседний код и не меняй интерфейс/формат данных без необходимости. Перед правкой существующего текста/кода проверь число совпадений; для скриптовых замен используй Python с `assert`.
4. **Проверь соразмерно задаче.** Сначала запускай целевые тесты (`node --test test/имя.test.js`). После завершения логического этапа запускай `npm run check` — он проверяет синтаксис, связи интерфейса/IPC и все тесты. Не запускай одну и ту же полную проверку повторно без изменения кода или иной причины.
5. **Не выпускай релиз автоматически после каждой правки.** Версию не повышай и архив не собирай, если автор явно не попросил релиз или не завершён согласованный релизный этап. Для релиза: обновить `version` в `package.json`, выполнить `npm run release`, передать созданный архив `../kabinet-<версия>.zip`. Команду установки/обновления сообщать только если это нужно для текущего релиза.
6. **Не заявляй о непроведённых проверках.** Приложение в этой среде может быть нельзя запустить; интерфейс автор проверяет самостоятельно. Если `npm`/зависимости недоступны, не пытайся устанавливать пакеты и собирать Electron — сообщи ограничение.

## Экономия контекста

- `renderer/app/NN-имя.js` — фрагменты одного общего скрипта, а не независимые модули. Функции и переменные доступны между фрагментами; следи за повторными объявлениями.
- `renderer/app.gen.js` — генерируемый файл: **не редактировать и не читать**, если задача не связана непосредственно с генератором. Он создаётся автоматически при сборке/проверке.
- Не загружай в контекст всю историю разработки. Текущая архитектура описана в `docs/PROJECT_NOTES.md`; история выпусков и решений — в `docs/DEV-CHANGELOG.md`. Открывай эти документы только когда они относятся к задаче.
- Не запускай сборку приложения (`npm run dist`, `npm run dist:win`, `npm run installer`) для обычной правки. Это отдельные операции выпуска/проверки сборки.

## Экономия ресурсов

- **Поиск:** всегда исключай генерируемое: `grep -rn --exclude=app.gen.js --exclude-dir=dist --exclude-dir=node_modules ...`. Иначе каждое совпадение в `renderer/app/` приходит дважды.
- **Большие файлы не читай целиком:** `renderer/style.css` (~52 КБ), `src/i18n-en.js` (~53 КБ), `test/gold-pos.js`, `main.js`, `src/project.js`. Находи место через `grep -n`, читай нужный диапазон (`sed -n 'N,Mp'`).
- **Тесты:** целевой — `node --test --test-reporter=dot test/имя.test.js` (при успехе почти без вывода). Полный `npm test` печатает ~30 КБ: не запускай его вместе с `npm run check` (check уже включает все тесты) и не выводи целиком, нужен только итог (`| tail -8`).
- **Проверки не повторять** без изменения кода. Для правки интерфейса достаточно `npm run check` один раз в конце этапа.
- **Документы:** `docs/DEV-CHANGELOG.md` (~30 КБ) читай только по версии или функции (`grep -n "^## 0.22"`, затем нужный фрагмент); `docs/PROJECT_NOTES.md` — нужный раздел.
- **Не пересказывай и не перечитывай** то, что уже прочитано в этой сессии; после правки проверяй изменённый фрагмент, а не весь файл.
- **Ответ автору короткий:** что изменено, какие проверки прошли, что не проверялось. Без пересказа кода и диффов.
- **Задачи ставятся точечно:** «ревизия всего проекта» — только по явной просьбе; иначе читай файлы задачи и их прямые зависимости.

## Архитектура в двух словах

- `main.js` — главное окно, меню, IPC, резервные копии, экспорт и данные приложения.
- `preload.js` — API `window.kabinet`; вызовы `call('канал')` должны соответствовать обработчикам `handle('канал', ...)` в `main.js`.
- `src/` — логика проекта, файловые операции, экспорт и текстовый анализ; значительная часть покрыта тестами.
- `renderer/` — HTML/CSS и интерфейс. Части `renderer/app/*.js` склеиваются в единый скрипт. `renderer/dist/app.js` — результат сборки.
- Данные автора нельзя терять: записи файлов должны оставаться атомарными, удаление пользовательских объектов — через предусмотренную Корзину. При изменении формата проверяй совместимость со старыми проектами.

## Основные команды

- `npm run map -- app` — карта функций интерфейса.
- `node --test test/имя.test.js` — целевые тесты.
- `npm test` — набор тестов, перечисленный в `package.json`.
- `npm run check` — полная проверка проекта.
- `npm run build` — сборка интерфейса.
- `npm run release` — полная проверка и архив обновления; только по необходимости.
- `npm run dist` — сборка macOS-приложения; не запускать для обычных правок.

## Обязательные ограничения

- Не менять авторский текст, данные и настройки без прямой необходимости задачи.
- Не добавлять тяжёлые зависимости без обоснования и согласования.
- Не менять публичные IPC-каналы и формат сохранения без проверки всех потребителей и обратной совместимости.
- При работе над текстовым анализом сохраняй приблизительный характер эвристик: не обещай абсолютную точность; добавляй регрессионные тесты на найденные ошибки.
- Не делай массовых переименований и архитектурных перестроек в рамках точечного исправления.

## Идея на будущее (решение автора: вернуться, когда у Кабинета накопится больше обновлений)
- Экосистема: Кабинет + приложение для карты мира + майнд-карта. Автор видит так: карта мира (генерация алгоритмами, без нейросети) → пользователь расставляет континенты, страны, города (вручную или автоматически) → по кнопке они уходят в Кабинет в отдельный раздел «География» и превращаются в карточки с иерархией (континент → страна → город) и привязкой к объекту на карте. Цель: автор не путается в географии своего мира.
- Договорённости: карта — источник правды о географии; в карточке хранится происхождение (идентификатор объекта), повторная отправка обновляет, а не дублирует; при конфликте названий программа спрашивает; обратную синхронизацию делать позже и осторожно; данные не терять (обратная совместимость, резервные копии).
- Майнд-карта без нейросети: ручная доска (узлы и связи), автоматическая схема «герой — глава — место» из уже имеющихся упоминаний (src/mentions.js), дерево из географии.
- Первый шаг, когда вернёмся: набросок полей раздела «География» в карточках Кабинета (по нынешнему устройству карточек).
